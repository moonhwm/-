# 玩具实验：KV 缓存前缀复用省多少——沙盒实测 + 幻 16 实操指南

- data_cutoff: 2026-08-29
- 性质：学习性实验（kvcache-lab 同构微缩版），沙盒 CPU 实跑，非仿真数字
- 真机复核：见 [PREFIX_REUSE_VERIFICATION.md](PREFIX_REUSE_VERIFICATION.md)（方向成立，量级下修）

## 一、实测结果（torch 手写 4 层 attention，前缀 N=2048、新增 M=64，CPU）

| 路径 | 耗时 | 含义 |
|---|---|---|
| A 无缓存：每轮全量重算（前缀+新增 prefill） | 274.4 ms/轮 | 每轮对话都重读全部历史 |
| B 前缀 prefill 一次（存 K/V） | 253.3 ms（一次性） | 历史只读一次 |
| B 增量（缓存复用，只算新增） | **14.3 ms/轮** | 每轮只算新 token × 缓存 |
| **每轮节省 / 加速** | **94.8% / 19.1×** | |

多轮累计（同一前缀反复对话）：

| 轮数 | 无缓存 | 有缓存 | 倍数 |
|---|---|---|---|
| 10 | 2.74s | 0.40s | 6.9× |
| 100 | 27.4s | 1.68s | 16.3× |

轮数越多，一次性 prefill 的成本被摊得越薄——**长会话=缓存复用收益最大场景**（22h 项目正是这种）。

## 二、外推：为什么官方说「40 万前缀+4K 新增差几个数量级」

注意力 prefill ≈ O(N²)，KV 缓存增量 ≈ O(N)/token：

| 前缀 N | 无缓存成本 | 增量成本 | 差距 |
|---|---|---|---|
| 2,048 | ×1 | ×1 | ×1 |
| 32,768 | ×256 | ×16 | ×16 |
| 400,000 | ×38,147 | ×195 | **×195** |

差距随 N 平方扩大。40 万前缀场景复用与否差约 195 倍（本实验参数下），继续拉长到 1M（K3 上下文）差距更大——这就是 Mooncake/外部 KV Cache 存在的理由。

## 三、与本项目对照

- 22h 长会话每轮都带着超长前缀推理——平台侧若每次都重算前缀，成本天文数字；线上必有前缀缓存（vLLM 保留策略旁证），只是**缓存不暴露为「可恢复检查点」**（宕机/换集群即丢）；
- 「外部 KV Cache 检查点」= 把这份缓存**持久化+同边界成对恢复**（KDA 递归状态与 MLA KV 块一起）——开源参考 kvcache-ai/Mooncake + AgentENV。

## 四、幻 16 实操指南（本机已跑通，见 kv_cache_lab.py / prefix_reuse_lab.py）

**路线 A（最轻，10 分钟）——transformers 直接测**：已完成，见 [RESULTS.md](RESULTS.md) 与 [PREFIX_REUSE_VERIFICATION.md](PREFIX_REUSE_VERIFICATION.md)。

**路线 B（生产级，半天）——vLLM + LMCache**：
1. 装 vLLM（幻 16 的 RTX 显卡 + WSL2/Linux）；
2. 按 LMCache 官方 quickstart 挂 CPU offload；
3. 跑 Qwen2.5-7B：开/关 prefix cache 各跑一次 8K 前缀+短问答，观察 TTFT（首 token 延迟）差异——预期 5–20×（社区经验值，未实测）。

**注意**：幻 16 显存 6GB 跑 7B 需量化（AWQ/GPTQ）；路线 A 的 distilgpt2 无压力。

## 五、复跑说明

本实验代码为 torch 手写微缩 attention（沙盒 CPU），参数 D=256/H=8/L=4/N=2048/M=64。数字会随硬件变化，**量级结论（每轮省 90%+、差距随 N 平方扩大）稳健方向，真机口径以复核文件为准**。

## top3_likely_wrong

1. 微缩 attention 无 FFN/归一化层，绝对耗时与真实 transformer 不同——比例结论（94.8%/19.1×）亦会随模型结构偏移，勿当生产基准（真机复核已证实下修至 81.6%/5.4×）；
2. 「40 万差 195×」是从 O(N²)/O(N) 标度律外推，真实工程有分块/稀疏注意力会削弱该比值；
3. 幻 16 路线 B 的 TTFT 预期倍数（5–20×）为社区经验值，未实测。
